# Independent production model calls — 1.1.8-yd.4.4

“全部生成” could fail in director planning after only 2,550 output tokens: the application subtracted an 1,800-token routing reservation from 12,000 and divided the rest among four phases. In the observed run, routing and extraction had actually used only 135 + 608 tokens. The model was not running out of its own context window.

New production starts retain one user-facing task. Each internal stage makes a fresh structured model request, reads the saved results needed by the next stage, and uses the configured model's single-request output limit. Output tokens are still recorded cumulatively, but these new calls do not compete for a shared 12,000-token allowance. Model-call, tool-step, image and video authorizations remain enforced; no automatic retry is added.

The server selects this mode for new HTTP and Socket.IO production starts that do not explicitly request a legacy `maxOutputTokens` total. Existing runs and explicit total-only API clients retain their original limits and checkpoints. Script-agent and special-purpose runs are unchanged. Checkpointed workspace snapshots after each text stage prevent a restarted worker from confusing its own later writes with a different input to an already completed stage.

The configured role limit can still tighten a request. Registered model `maxOutputTokens` metadata is respected. For the official HTTPS `api.deepseek.com` endpoint, DeepSeek V4 Pro/Flash models use the documented 384,000-token output capability when the role is set to automatic. That number is not inferred from the 1M context window and is not applied to arbitrary relay endpoints. Other models without declared output metadata or a configured limit use their provider default; the application does not claim that an unknown default is the model's maximum. Sources: [official model details](https://api-docs.deepseek.com/quick_start/pricing/), [official integration configuration with numeric limits](https://api-docs.deepseek.com/quick_start/agent_integrations/pi_mono/).

The production panel shows independent-call mode and cumulative actual text usage. No per-stage manual quota form or additional task cards are introduced. This release changes neither the definition of derived assets nor the existing image/video generation authorization.

Validation includes an isolated PostgreSQL four-stage run producing 18 distinct shots totaling 60 seconds with 17,750 reported output tokens, recovery of the same task without replaying its saved director plan, preserved prior work after a structured-output failure, explicit legacy-budget behavior, and official-versus-relay model-limit resolution. The compiled application/browser test inspects the actual SDK HTTP request against a local provider with a declared 24,000-token cap, and checks browser reopening and process restart. All model/media generation in these regression tests uses isolated simulated providers; no failed user task or paid generation is replayed.
